# Платформа подбора ИТ-специалистов с верифицированным профилем ФСП

Сопроводительная документация · команда Null Pointers · ЛЦТ 2026

## 1. Что это

Веб-платформа с обратной механикой подбора: кандидат проходит опрос по
специализации и адаптивное тестирование, получает категорию
(специализация × грейд) и подтверждённые достижения ФСП; работодатель
описывает потребность текстом, получает объяснимую подборку и сам
направляет приглашение с уровнем заработной платы. Контакты кандидата
раскрываются только после принятия приглашения или самостоятельного
отклика.

## 2. Архитектура

Компонентная схема — presentation/assets/architecture.png.

Модульный монолит с явным разделением слоёв (ТЗ 3.5):

| Слой | Технология | Назначение |
|---|---|---|
| Frontend | Next.js 14, TypeScript, Tailwind | кабинеты кандидата и работодателя |
| Backend API | Python 3.12, FastAPI, SQLAlchemy 2 (async) | бизнес-логика, OpenAPI |
| Хранение | PostgreSQL 16 + pgvector | данные, векторный индекс (roadmap) |
| Кеш/лидерборды | Redis | лимитер запросов (скользящее окно), живые лидерборды категорий |

Модули backend: `auth`, `profiles` (в т.ч. PDF-сертификат категории с QR),
`testing` (IRT/CAT, банк заданий, конструктор тестов работодателя,
демо-квиз без регистрации), `matching` (Score, подборка, слепой найм),
`interaction` (вакансии, приглашения, отклики, микрозадачи, воронка найма),
`leaderboard` (топ категории на Redis ZSET), `fsp` (мок-реестр
достижений), `admin` (демо-данные, сброс демо в один запрос).
Модули изолированы сервисами и схемами — распилены на сервисы
без переписывания.

Обязательные правила ТЗ реализованы на сервере:
- зарплата (вилка «от–до») обязательна и в вакансии, и в приглашении;
- контакты раскрываются только после принятого приглашения/отклика
  (проверка на сервере, не на клиенте);
- статусы взаимодействий (sent → viewed → accepted/declined) видны
  обеим сторонам;
- регистрация по email с подтверждением;
- кандидат без истории ФСП — валидный сценарий.

## 3. Механика тестирования

### 3.1 Психометрическое ядро (IRT)

Каждое задание банка имеет калиброванные параметры модели IRT 3PL:
- `a` — дискриминативность (разделяет слабых и сильных);
- `b` — сложность;
- `c` — поправка на угадывание.

Оценка способностей θ (тета) вычисляется методом EAP (апостериорное
среднее по сетке, prior N(0,2)). Ключевое свойство: θ инвариантно к
набору заданий — кандидаты, отвечавшие разные варианты, сравнимы между
собой. Это решает дилемму ТЗ: единый банк запрещён (утечка), свободная
генерация несопоставима.

Пороги грейдов по θ: < -0.5 → Junior, < 0.5 → Middle, < 1.5 → Senior,
иначе Lead. Смена грейда ограничена: не чаще 1 раза в 90 дней
(повышение; тест на уровень ниже разрешён всегда).

### 3.2 Адаптивный движок (CAT)

- старт с уровня заявленного грейда;
- после каждого ответа θ пересчитывается, следующее задание выбирается
  по максимуму информационной функции I(θ);
- остановка по стандартной ошибке SE(θ) ≤ 0.30 или при исчерпании лимита
  (12 заданий / пула);
- итого: точный грейд за 10–15 заданий.

### 3.3 Устойчивость к утечкам (обоснование)

1. Параметризованные шаблоны: тело задания генерируется при каждой
   выдаче (случайные данные) — «слитый» ответ бесполезен у следующего
   кандидата.
2. Варианты ответов перемешиваются при каждой выдаче; в сессии задания
   не повторяются.
3. Контроль экспозиции: после 50 показов задание деактивируется —
   скомпрометированный набор вымывается автоматически.
4. LLM-конвейер пополнения (roadmap): генерация черновиков → эталонное
   решение → пилотная калибровка → банк; LLM не оценивает людей.

### 3.4 Честность результатов (анти-списывание)

- фиксация времени на каждый вопрос; верный ответ быстрее порога
  (3.5 с — выбор, 12 с — свободный ответ) = сигнал;
- отслеживание ухода со вкладки (Page Visibility API): уход > 8 с +
  верный ответ = сигнал; после ухода тест начинается заново;
- показатель честности сессии (integrity): −15% за сигнал; виден
  работодателю и снижает вклад «стабильности» в рейтинге множителем
  (0.6 + 0.4 × integrity) — максимум −0.04 от Score из 1.0; балл, грейд
  и место в категории честность не меняет;
- попытки не ограничены — подтверждается лучший результат категории.

### 3.5 Проверяемый сертификат категории

Кандидат с присвоенной категорией выгружает PDF-сертификат
(`GET /api/candidate/certificate.pdf`): специализация, грейд, балл, QR-код.
QR ведёт на публичную страницу `GET /api/verify/{user_id}/{signature}` —
сервер заново вычисляет HMAC-SHA256 от (версия, кандидат, специализация,
грейд, балл) и сверяет с подписью в URL. Подделка или правка категории
в обход теста определяются сразу; страница показывает «подлинный» или
«не подтверждён». Ключ подписи — секрет сервера.

## 4. Механика подбора и категоризация

Категория = специализация × грейд, присваивается только по результату
тестирования (не по резюме). Кандидат может иметь несколько категорий
(по одной на направление).

Объяснимый рейтинг внутри категории:

```
Score = 0.45·σ(θ) + 0.20·FSP + 0.15·Freshness + 0.10·Match + 0.10·Reliability
```

- σ(θ) — тестовая способность;
- FSP — достижения ФСП: вес уровня × затухание по свежести (0.85^лет);
- Freshness — экспоненциальное затухание активности (период ~3 недели),
  поддерживается решением микрозадач;
- Match — покрытие стека потребности работодателя (MVP: пересечение
  тегов; roadmap: эмбеддинги pgvector);
- Reliability — f(SE) и согласованность повторных прохождений,
  умноженная на показатель честности.

Работодатель видит разложение вкладов и текстовое обоснование каждого
кандидата. Подборка: NLP-парсинг потребности (MVP: правила + словарь
стеков; roadmap: эмбеддинги/LLM) → жёсткий фильтр по категориям →
ранжирование. Скорость: 25–48 мс на 150 кандидатах (замер в e2e, SLA 200 мс).

Топ-10 категории живёт в Redis (ZSET `leaderboard:{spec}`): обновляется
при завершении CAT-теста (`ZADD GT`) и отдаётся через
`GET /api/leaderboard/{spec}` — рейтинг показан в кабинете работодателя
(кого звать на собеседование); кандидатам топ не показываем, чтобы не
сбивал фокус перед тестом.

Слепой найм (тумблер в кабинете работодателя, `PUT /api/employer/blind`):
в подборках имена заменяются на «Кандидат №XXXX», фото скрыты — решение
принимается по категории, стеку и честности теста; личность открывается
после принятия приглашения. Воронка найма (`GET /api/employer/funnel`):
вакансии → отклики → приглашения → принято, конверсия и среднее время
ответа кандидата.

## 5. Свои тесты работодателя

1. Авторесерч: по описанию потребности выполняется поиск в интернете
   (DuckDuckGo), извлекаются навыки (фолбэк — база знаний);
2. черновик собирается автоматически из банка (равномерное покрытие
   шкалы сложности);
3. работодатель оставляет/удаляет вопросы, добавляет свои (с ответами),
   может заменить весь тест; каждый вопрос показывается образцом —
   живой текст на языке теста (`code_language`) с помеченным верным
   ответом, один и тот же при каждой загрузке черновика;
4. публикация закрыта, пока работодатель не подтвердит галочкой, что
   посмотрел примеры вопросов; опубликованный тест прикрепляется к
   приглашению; сессия кандидата идёт по нему (пул ограничен черновиком).

## 6. Валидация

Процедура: симуляции на синтетических кандидатах (графики — presentation/assets).

| Метрика | Значение | Цель |
|---|---|---|
| corr(θ, истинная способность), 1500 кандидатов | 0.955 | ≥ 0.90 |
| Надёжность rxx (два независимых прохождения) | 0.913 | ≥ 0.90 |
| Согласованность грейдов (κ Коэна) | 0.606 (совпадение 72%) | ≥ 0.60 |
| Восстановление сложности заданий, corr | 0.981 (57 из 60) | — |
| Скорость подборки, 150 кандидатов | 25–48 мс | < 200 мс |
| Подбор «вакансия → кандидат»: Precision@10 / MRR / nDCG | 0.450 / 0.306 / 0.828 | — |

Test-retest подтверждается через rxx; дискриминативность заданий —
информационными кривыми (assets/irt_curves.png). В ходе валидации
найдены и исправлены дефекты: формула информации 3PL (была 2PL),
MLE → EAP (стабильность начала теста), бесконечный цикл генератора
вариантов, калибровка порогов на наблюдаемой шкале.

Сквозной сценарий проверяется автоматически: backend/scripts/e2e_smoke.py
(36 проверок: регистрация → тест → категория → ФСП → подборка → свой
тест → приглашение → принятие → раскрытие контактов → отклики, плюс
демо-квиз, лидерборд категории, PDF-сертификат, отклонение поддельной
подписи verify, слепой найм и воронка найма).

## 7. Схема интеграции с реестром ФСП

Контракт спроектирован командой (API ФСП в хакатоне не предоставляются):

```
Кандидат → POST /api/fsp/link/{fsp_id}
Платформа → Реестр ФСП: GET /registry/{fsp_id}          (мок сейчас)
Реестр → подписанная запись достижений (HMAC-SHA256)
Дальше: verifiable credentials + OIDC (Keycloak ФСП ID)
```

Запись достижений: kind (tournament/olympiad/event), title, level
(international/national/regional), result, year. Вес вклада калибруется
совместно с ФСП после хакатона. Случай «истории нет» — вклад 0.

## 8. Безопасность

- Шифрование PII на уровне приложения: AES-256-GCM; ключ выводится
  HKDF из секрет-ключа сервера; AAD-привязка шифртекста к
  (таблица, поле). В БД ФИО/контакты/summary/контакты работодателя —
  шифртекст; на сайте — обычные данные.
- Пароли: bcrypt, 12 раундов (~210 мс/проверка).
- JWT (HS256; roadmap: RS256/OIDC под Keycloak), роли в токене,
  проверка роли в каждом запросе.
- Rate limiting: скользящее окно в Redis (ZSET), auth 20/мин с IP,
  остальное 240/мин → 429; при недоступности Redis — деградация в
  локальный буфер процесса.
- Сертификат категории: PDF с QR; подпись HMAC-SHA256 от (версия,
  кандидат, специализация, грейд, балл) под ключом сервера — публичная
  verify-страница сверяет её со свежей, правка категории в БД обнаруживается.
- 152-ФЗ: согласие на обработку (без него кандидат не попадает в
  подборку), приватность профиля, раскрытие контактов только после
  принятия.
- Границы: email хранится открытым (идентификатор входа; roadmap:
  слепой индекс), анти-DDoS многослойен (nginx/CDN — уровень деплоя).

## 9. API

OpenAPI-спецификация: http://localhost:8000/api/openapi.json,
Swagger UI: /api/docs. Основные группы:

- `auth`: register, confirm, login, refresh;
- `testing`: specializations, survey, answer, status, history;
  демо-квиз: `POST /demo/quiz/start?spec=&language=`,
  `POST /demo/quiz/answer` (публичные, без регистрации; язык заданий —
  python / javascript / c++ / c# / java);
- `candidate`: profile, privacy, invitations, applications, microtasks,
  metrics, photo, certificate.pdf (PDF с QR);
- `verify/{user_id}/{signature}` — публичная сверка подписи сертификата;
- `leaderboard/{spec}` — топ-10 категории (Redis ZSET);
- `matching`: need → подборка, search;
- `employer`: profile, tests (draft/items/publish), vacancies,
  invitations, candidate/{id}, funnel (воронка найма), blind (слепой найм);
- `interaction`: vacancies CRUD, invitations, applications, microtasks;
- `fsp`: registry/{id}, link/{id};
- `admin`: seed (демо-данные; `?reset=true` — полный сброс и пересид),
  validate (живая валидация CAT).

Все эндпоинты документированы (запросы, ответы, коды ошибок) в Swagger.

## 11. Сборка, развёртывание, запуск

### Docker Compose (всё сразу)

```bash
docker compose up -d --build     # postgres + redis + api + frontend → :8000 и :3000
```

### Фронтенд вручную (для разработки, с hot reload)

```bash
cd frontend
npm install
npm run dev                      # http://localhost:3000
```

### Демо-данные и сброс

```bash
curl -X POST localhost:8000/api/admin/seed              # если база пуста
curl -X POST "localhost:8000/api/admin/seed?reset=true" # полный сброс и пересид
```

Детерминированный сид (seed=2026): 150 кандидатов с категориями, 8
специализаций, вакансии, живая активность (отклики, приглашения,
воронка). У demo_cand_001 в истории уже лежит одна попытка (бэкенд,
балл 12, junior) — кабинеты не выглядят пустыми. Демо-аккаунты:
techlog@techlogistics.ru / Employer2026!;
demo_cand_001@example.ru / Candidate2026!. Демонстрационные ID реестра
ФСП: FSP-2026-0001…0003 (есть история), FSP-9999-999 (истории нет).

### Проверка

```bash
cd backend && python scripts/e2e_smoke.py    # 36 проверок, нужен живой api
```

Требования: обычная машина, ~2 ГБ RAM для контейнеров.
